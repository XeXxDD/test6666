## SC2 Editor — выжимка текущей отладки

### Цель

Найти внутренний механизм выбора цветов элементов SC2 Editor и впоследствии менять цвета условно по состоянию:

* красный → свой цвет;
* зелёный → свой цвет;
* другие состояния → свои цвета.

Не хотим делать простую глобальную замену `COLORREF`.

Предпочтительный путь — **минимальное вмешательство**, сначала понять внутреннюю цепочку выбора цвета.

---

# Что уже доказано

## 1. `SetTextColor` — реальная конечная точка

Hook `HookSetTextColor` ловит цвета кнопок.

Основные варианты:

```text
0xA000   → Variable, зелёный вариант
0x804040 → Value, красный вариант
```

Но это **конечный результат**, а не обязательно место выбора цвета.

---

## 2. Найдена внутренняя цветовая функция

RVA:

```text
0x1F4ED30
```

Внутри есть:

```asm
mov rdi, rdx
mov rsi, rcx
```

и проверки:

```asm
test byte ptr [rdx+18h], 1
```

а позже:

```asm
mov ecx,[rdx+18h]
shr ecx,2
test cl,1
```

То есть используются:

```text
[RDX+0x18].bit0
[RDX+0x18].bit2
```

---

# V93–V99: восстановление контекста

Первоначально `HookSetTextColor` видел только конечный вызов.

Через два `RtlVirtualUnwind` получили настоящий SC2 caller:

```text
FRAME=2
RIP=00007FF6376BEDC8
```

Это настоящий call site `SetTextColor`.

Из него удалось восстановить исходные регистры:

```text
RDI = original RDX
RSI = original RCX
```

То есть можно исследовать настоящие `RCX/RDX`, с которыми работает SC2.

---

# V95–V99: состояние

Для `Variable`:

```text
color = 0xA000
RDX+18 bit0 = 0
```

Для `Value`:

```text
color = 0x804040
RDX+18 bit0 = 1
```

Также наблюдались:

```text
RDX+20 = 0
RDX+28 = 1
```

`RCX` у повторных вызовов одного элемента мог оставаться одинаковым, тогда как `RDX` менялся.

Предварительная модель:

```text
RCX = color-data object
RDX = state object
```

Но это **гипотеза**, не окончательно доказанный факт.

---

# Эксперимент с изменением bit0

Пробовали принудительно менять:

```text
[RDX+0x18].bit0
```

с:

```text
0 → 1
```

Лог подтверждал:

```text
before=0x0
after=0x1
originalBit0=0
forcedBit0=1
```

Но визуально цвет не изменился.

Эксперимент признан неудачным.

Вывод:

> `RDX+18.bit0` либо не является единственным фактором выбора цвета, либо изменение происходит слишком поздно/результат позже перезаписывается, либо этот конкретный state не определяет непосредственно итоговый цвет.

Поэтому дальше на bit0 не зацикливаемся.

---

# Почему отказались от других путей

### Debugger

Нестабилен/приводит к падению SC2.

### DetourAttachEx

Не подходит для нужного варианта.

### VirtualProtect

Много раз проверяли:

```text
VirtualProtect result=0 error=87
```

Проверка `VirtualQuery` и реального Windows API не дала решения.

### NtProtectVirtualMemory

Тоже не помог:

```text
status=0xc0000045
```

Поэтому **прямое изменение машинного кода SC2 пока не используем**.

### Прямая подмена COLORREF в SetTextColor

Приводила к зависаниям/падениям либо не давала нужного результата.

# Перешли к восстановлению цепочки вызовов

Решили исследовать не весь SC2 подряд, а восстанавливать цепочку:

```text
SetTextColor
    ↓
1F4ED30
    ↓
1F4EDC8
    ↓
caller/frame 3
    ↓
поиск объекта по HWND
    ↓
следующий внутренний объект/метод
```

Для этого уже используются:

```text
InspectColorCallSiteV93
DumpCodeAtRvaV77
AnalyzeRelativeCallsV105
CaptureSC2CallerV96
```

# V106–V107

Удалось получить третий frame и исследовать код вокруг него.

Важный результат:

из `RSI+0x18` получается настоящий HWND.

Например:

```text
RSI+0x18 = 0x7F0810
```

что соответствует HWND исследуемого элемента.

Это позволило перейти к поиску внутреннего объекта по HWND.

---

# V108 — найден внутренний поиск

В SC2 обнаружена функция:

```text
RVA = 0x1F31080
```

Она работает примерно так:

```asm
mov rdx,[rip+061ACA31h]
lea r8,[rip+061ACA2Ah]
...
cmp [rax+20h], rcx
...
cmp rax,r8
...
mov rax,[rax+28h]
```

Первоначально displacement был ошибочно записан как:

```text
0x61CA31
0x61CA2A
```

Из-за этого получали:

```text
ROOT=CCCCCCCC...
```

Ошибка исправлена.

Правильные little-endian displacement:

```text
0x061ACA31
0x061ACA2A
```

После исправления:

```text
ROOT=1a69859fbd0
```

то есть нормальный адрес.

---

# V108 — результат поиска

После исправления получили:

```text
[V108] FRAME3 HWND=15066e
ROOT_ADDR=7ff63d84dab8
ROOT=1a69859fbd0

[V108] RESULT_OBJECT=1a68f807ea0
RESULT_KEY=1550566
ITERATIONS=6

[V108] FINAL_OBJECT=1a68f807ea0
VTABLE=1a69859fb50
```

Для других HWND также получались нормальные ROOT/RESULT_OBJECT.

То есть **V108 уже действительно выполняет внутренний поиск SC2**, а не читает случайную память.

# V108-1 / V108-2 — важное открытие

В исходном коде найденного участка есть:

```asm
49 8B 00
FF 90 50 01 00 00
```

то есть:

```asm
mov rax,[r8]
call qword ptr [rax+150h]
```

Поэтому первоначально предположили:

```text
FINAL_OBJECT
    ↓
[VOBJECT+0]
    ↓
VTABLE
    ↓
[VTABLE+0x150]
    ↓
virtual function
```

Но V109 показал, что это пока **не подтверждено**.

# V109

Для `FINAL_OBJECT` вывели:

```text
VTABLE+0x140
VTABLE+0x148
VTABLE+0x150
VTABLE+0x158
VTABLE+0x160
```

Получались значения вроде:

```text
VTABLE+0x140 = 5165736e6f707365
VTABLE+0x148 = 79726575
VTABLE+0x150 = 486920e100000003
VTABLE+0x158 = 73
VTABLE+0x160 = 1b801428470
```

Это **не похоже на обычную таблицу указателей на функции**.

Особенно:

```text
VTABLE+0x150 = 486920e100000003
```

не является нормальным canonical x64 адресом функции вида:

```text
00007FF6........
```

Поэтому нельзя пока утверждать:

```text
FINAL_OBJECT → обычная C++ vtable
```

# Что нужно проверить дальше

Самая важная следующая проверка:

для:

```text
RESULT_OBJECT
```

прочитать:

```text
OBJECT+0x00
OBJECT+0x08
OBJECT+0x10
OBJECT+0x18
OBJECT+0x20
OBJECT+0x28
OBJECT+0x30
```

Особенно:

```text
OBJECT+0x28
```

Причина:

исследуемая функция `1F31080` в одной из веток делает:

```asm
mov rax,[rax+28h]
```

То есть вполне возможно, что `RESULT_OBJECT` — это **не конечный объект**, а промежуточный узел, из которого SC2 получает другой объект через `+0x28`.
